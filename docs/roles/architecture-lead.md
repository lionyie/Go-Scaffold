# Architecture and Tech Lead Guide

[English](architecture-lead.md) | [简体中文](architecture-lead.zh-CN.md)

> Who this is for: the architect or tech lead who owns the repo's boundaries, code-generation pipeline, tech debt, and review standards for a Go (Kratos v3) + TypeScript monorepo.

## Responsibilities

- Own the layer boundaries and the five boundary rules; reject cross-layer imports in review.
- Own the generation pipeline (`pnpm run generate`) and the do-not-edit set of generated files.
- Own the permission catalog contract (`contracts/permissions.yaml`) and its verification.
- Track known inconsistencies and tech debt; schedule paydown instead of letting it drift.
- Set review standards: every proto or permission change ships with regenerated code and passing gates.

## Layer diagram and dependency direction

From [Architecture](../architecture.md#layers):

```text
apps/web, apps/admin          Vue 3 + Vite + Vuetify 4
        │  HTTP/JSON (protojson)
services/internal/server      Kratos HTTP/gRPC, authn/authz, OAuth callbacks
services/internal/service     proto <-> biz adapters
services/internal/biz         usecases, repository interfaces
services/internal/data        GORM repositories, seed, health
services/internal/auth        JWT, password hashing, OAuth provider registry
services/internal/plugin      experimental runtime plugin loader
services/internal/webui       embedded web + admin SPA handler
        ▲ generated by buf
contracts/proto/**/v1         protobuf contracts
```

| Layer | May import | Must not import |
| --- | --- | --- |
| `server` | `service`, `authz`, `middleware` | `data` directly |
| `service` | `biz`, generated `services/api` types | `data`, `server` |
| `biz` | `data` interfaces it defines | `service`, `server` |
| `data` | GORM, conf | anything above |
| extensions | `biz`, `data`, `server/authz`, `extensions/registry` | — |

Core code must never import a specific extension. HTTP middleware runs in the order recovery -> logging -> LoginRateLimit -> Authn -> Authz (`services/internal/server/http.go`).

## The five boundary rules

Summarized from [Architecture: Boundaries](../architecture.md#boundaries):

1. `contracts/` holds only `.proto` files and `permissions.yaml` — no implementation code.
2. `services/api/` is generated; the only hand-written file is `services/api/identity/v1/redact.go`.
3. `packages/api-client/{generated,src/generated}`, `packages/shared/src/permissions.gen.ts`, and `*_gen` packages under `services/internal/` are generated — never edit by hand.
4. All `dist/` output (`apps/*/dist`, `runtime-plugins/*/dist`, `services/internal/webui/dist`) is build output and gitignored.
5. Each build unit owns its manifest (`services/go.mod`, each `package.json`, `deploy/docker/Dockerfile`); root files only orchestrate.

## Single source of truth and the generation chain

`contracts/proto/**/v1/*.proto` plus `contracts/permissions.yaml` are the source of truth. `pnpm run generate` produces:

| Source | Generated output |
| --- | --- |
| `contracts/proto/**/v1` | Go protobuf/gRPC/Kratos HTTP in `services/api/**` |
| `contracts/proto` | OpenAPI at `packages/api-client/generated/openapi.yaml`, TS schema at `packages/api-client/src/generated/schema.d.ts` |
| `services/internal/conf/conf.proto` | `services/internal/conf/conf.pb.go` |
| `contracts/permissions.yaml` | `services/internal/pkg/rbac/permissions_gen.go`, `packages/shared/src/permissions.gen.ts` |
| `services/cmd/api/wire.go` | `wire_gen.go` |
| `extensions/installed.lock.json` | `*_gen` registries and `apps/*/src/router/features.gen.ts` |

Do-not-edit set: `services/api/**` (except `identity/v1/redact.go`), `conf.pb.go`, `permissions_gen.go`, all `*_gen` files/dirs, `packages/api-client/generated/**`, `packages/api-client/src/generated/**`, `apps/*/src/router/features.gen.ts`. CI reruns `generate` and fails on any `git diff`.

## API Reference (Swagger UI)

The same `protoc-gen-openapi` generator produces two committed documents:

- `packages/api-client/generated/openapi.yaml` for the TypeScript client.
- `services/internal/swagger/generated/openapi.yaml`, embedded in the Go binary
  and served by Swagger UI at `/swagger/` in non-production environments.

Treat both as generated outputs (see the do-not-edit set above). The exposure
policy is `swagger.enabled` in config plus a hard `APP_ENV=production` disable;
review any change that weakens the production gate. See
[Development · API reference](../development.md#api-reference-and-swagger-ui).

## Extension vs runtime plugin vs core

| | Core | Feature extension | Runtime plugin (experimental) |
| --- | --- | --- | --- |
| Lives in | `services/internal/`, `apps/` | `extensions/templates/`, installed by `scripts/module.mjs` | `runtime-plugins/<id>/` |
| Lifecycle | Always compiled in | Copied into the tree at install time, tracked by `installed.lock.json` | Loaded at server startup |
| Can add proto/Go services | Yes | Yes (`codegen: true` reruns generate) | No |
| Can add SPA routes/menus | Yes | Yes, via generated `features.gen.ts` | Yes, via `plugin.json` |
| Authz integration | `authz/mapping.go` | `authz/extensions_gen.go` entries | Self-authenticates under `/proxy/plugins/` |

Choose core for capabilities every deployment needs (auth, RBAC, user management). Choose an extension for optional but first-class features (OAuth providers, vertical slices). Choose a runtime plugin for host-agnostic panels or experiments that must not touch codegen or the binary.

## Production semantics of auth and RBAC

- JWT access token 15 minutes, rotating refresh token 7 days; passwords are bcrypt; refresh tokens are stored as SHA-256 hashes.
- Login is rate limited to 5 failures per IP+username per minute (HTTP 429).
- The seeded `admin / admin123` account has `must_change_password=true`; permissioned operations fail with `MUST_CHANGE_PASSWORD` until rotated, enforced by middleware. Production fails fast on an unrotated seed password; set `SCAFFOLD_SEED_ADMIN_PASSWORD`.
- `is_admin=true` bypasses permission checks; unknown authz operations fail closed with 403.
- The authz map (`services/internal/server/authz/mapping.go`) must cover every generated operation; `pnpm run verify-authz` enforces this.
- OAuth `OAuthStore` is in-memory: state and one-time tickets are lost on restart and not shared across replicas. Replace with Redis/DB before horizontal scaling.
- `/proxy/plugins/` and `/api/v1/auth/oauth/` routes bypass the Kratos middleware chain and authenticate themselves.

## Single binary, two SPAs

The built Go server serves both apps: `/` from `apps/web/dist`, `/admin/` from `apps/admin/dist`, with longest-prefix mount selection in `services/internal/webui`. The prefixes `api/`, `proxy/`, `healthz`, and `readyz` are reserved and never fall back to an SPA. Static assets are cached for 1 year; `index.html` is served no-cache. JSON on the wire is protojson: camelCase fields, enum names, and 64-bit integers as strings.

## Known inconsistencies

This is the authoritative list; fix forward, do not paper over:

- `packages/shared/src/index.ts` exports `APP_NAME = "Vela"` while the repo brand is otherwise "scaffold".
- Both `apps/*/src/i18n/index.ts` persist the locale under the key `vela.locale`.
- `apps/web/src/api/client.ts` sends the header `x-vela-retried` while `apps/admin/src/api/client.ts` sends `x-scaffold-retried`.
- `apps/admin/src/directives/permission.ts` defines `vPermission` but it is never registered in `main.ts`.
- `PageHeader` is imported per view while `AppSnackbar` and `ConfirmDialog` are globally registered in both `main.ts` files.
- There are no frontend tests; every package test script is `echo no-tests`.
- The OAuth store is in-memory only (see above).
- The login rate limiter is also in-memory, so failed-login limits are enforced per replica, not globally.
- `services/internal/data/migrations/` contains only READMEs — no migration tooling yet.
- CI builds the Docker image but never pushes it (`.github/workflows/ci.yml`, `docker` job, main branch only).

## Tech debt and evolution suggestions

Ordered by impact; none of this is done yet:

1. Add frontend testing (Vitest + component tests) and replace the `echo no-tests` placeholders.
2. Provide a persistent `OAuthStore` implementation (Redis or SQL) for multi-replica deployments.
3. Introduce real database migrations under `services/internal/data/migrations/` instead of GORM auto-migrate plus seed.
4. Unify branding leftovers (`APP_NAME`, `vela.locale`, `x-vela-retried`) behind one name, with a migration note for stored localStorage keys.
5. Register `vPermission` globally or remove the directive; decide one pattern for global UI components.
6. Add Docker push to CI behind a tag/release trigger if publishing images becomes a requirement.

## Change review checklist

- [ ] Proto changed -> `pnpm run generate` rerun, generated diff committed, no hand edits in generated paths.
- [ ] New permission -> added to `contracts/permissions.yaml`, mapped in `services/internal/server/authz/mapping.go`, `pnpm run verify-authz` passes.
- [ ] Cross-layer imports checked (`server -> service -> biz -> data` only; core never imports an extension).
- [ ] Generated files untouched by hand; CI codegen job would produce zero `git diff`.
- [ ] `pnpm run typecheck`, `pnpm run lint:web`, and `go -C services test ./...` pass.
- [ ] Docs updated (`docs/architecture.md`, `docs/auth.md`, or this series) when behavior or boundaries move.
